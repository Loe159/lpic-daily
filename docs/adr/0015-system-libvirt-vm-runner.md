# ADR 0015 — System libvirt VM control plane

Status: **Accepted — 2026-09-27**

## Decision

Phase 2 uses the local **qemu:///system** libvirt instance while the LPIC Daily process itself remains an ordinary unprivileged user.

The initial Go control-plane client is the pure-Go `github.com/digitalocean/go-libvirt` RPC implementation, pinned to an exact pseudo-version and hidden behind a project-owned adapter interface.

VM state uses immutable trusted base images plus disposable QCOW2 overlays.

## Why qemu:///system

Phase 2 requires isolated libvirt networks and later multi-machine scenarios. The system QEMU driver is libvirt's normal path for managed virtual networks and provides the distro's standard QEMU security/confinement integration.

LPIC Daily does not run setuid/root and does not invoke QEMU directly. Access is granted or denied by libvirt/polkit.

`qemu:///session` remains a possible reduced future mode, but is not the canonical backend because its networking/security behavior differs from what the full curriculum needs.

## Allowed libvirt scope

The adapter may create/manage only resources satisfying all of these rules:
- resource name starts with `lpic-daily-`;
- generated domain/network XML carries the LPIC Daily namespaced ownership marker plus a stable owner scope derived from the effective UID and VM state root; every managed-resource lookup and discovery/reaping operation requires both the marker and matching scope, never the name prefix alone;
- domain XML is generated by project code, never supplied verbatim by curriculum;
- base disk comes from the trusted image catalog;
- writable disks are LPIC Daily-owned overlays/scratch disks;
- no host PCI/USB/device passthrough;
- no host filesystem mounts/shared folders;
- no SPICE clipboard/host integration;
- no arbitrary QEMU command-line extension from content;
- networking is none or an LPIC Daily-owned isolated network with no forwarding;
- isolated-network subnet allocation is serialized through one root-provisioned host-global lock under `/var/lib/libvirt/images/lpic-daily/`, because `qemu:///system` network state is shared across users and custom state roots;
- memory/CPU/disk/time limits are bounded by project policy.

## Client dependency

Use the DigitalOcean pure-Go libvirt RPC client for the Phase-2 spike because it avoids a CGO/native-libvirt build dependency and is actively maintained.

Because its own project does not promise a stable public API:
- pin the exact module revision;
- no dependency type crosses `internal/runner/libvirt`;
- project tests target our adapter contract;
- an upstream API change should require changes in one package only.

If required libvirt APIs are missing or the dependency becomes unsuitable, the fallback is the modern upstream `libvirt.org/go/libvirt` binding. That switch must not affect curriculum or runner consumers.

## Image identity

A lab's `image_ref` is an opaque trusted image ID, not a path or URL.

The image catalog resolves it to a locally installed image and verifies SHA-256 before first use/run according to cache policy. Floating tags and runtime downloads from curriculum are forbidden.

## Overlay lifecycle

```text
trusted base image (read-only)
        |
        +--> run overlay qcow2
                 |
                 +--> disposable domain
                 |
                 +--> destroy/reset => remove overlay
```

Base images and overlay/scratch state default below `/var/lib/libvirt/images/lpic-daily/<uid>/`, provisioned once by the narrow admin script and thereafter writable by the ordinary LPIC Daily user. This keeps qemu:///system disks outside private home/XDG trees and within the normal libvirt SELinux/sVirt image hierarchy. Explicit absolute image/state overrides remain possible for operators that provide equivalent DAC/MAC policy. Curriculum cannot choose any host path.

## Failure behavior

Missing KVM/libvirt/qemu-img, failed polkit authorization, unknown image ID, checksum mismatch, unsupported firmware, unavailable isolation or cleanup failure are surfaced as errors. VM labs also fail closed when the LPIC Daily process has effective UID 0.

There is no container fallback for a lab declared as `libvirt` and never a host-shell fallback.

## Security follow-up

Before Phase 2 exit:
- destructive host-sentinel integration test on a real libvirt/KVM host;
- verify generated domain XML contains no host-device/filesystem passthrough;
- prove isolated network has no forwarding;
- prove base image is unchanged after run/reset;
- cleanup/reaper test for abandoned domains/overlays/networks.


## Serial console capability

The VM backend exposes serial-console access as the optional project-owned
`runner.ConsoleRunner` capability rather than adding console methods to every
runner implementation.

The concrete RPC adapter uses libvirt's bidirectional domain-console stream
against the already-generated `<serial type="pty">` / `<console type="pty">`
device. It always:
- resolves an LPIC Daily-managed domain by exact name;
- uses the default serial device (no curriculum-supplied device name);
- opens with zero force/safe flags by default;
- requires the domain to be active before the backend exposes the stream;
- never forwards host credentials, files, devices or sockets.

The CLI exposes this stream only through the explicit `:console` surface. Ctrl-] returns to LPIC Daily during normal use; session-context cancellation interrupts the disposable domain console so a blocked stream cannot outlive the lab timeout. Terminal state is restored on every return path.


## Structured storage probe

The VM backend implements the optional `runner.StorageProbe` capability through
QEMU Guest Agent structured execution.

The probe runs fixed project-owned argv only:
- `/usr/bin/lsblk --json --bytes --output PATH,TYPE,FSTYPE,MOUNTPOINT,PTTYPE,SIZE`;
- `/usr/bin/cat /proc/swaps`.

It flattens the resulting device tree into typed block-device observations and
marks active swap devices from the kernel's `/proc/swaps` view. Curriculum
cannot replace those probe commands. Storage checkers compare final state, not
the learner's command sequence.


## CLI backend dispatch checkpoint

`lpic lab run` now dispatches from the lab's declared backend. A `libvirt` lab loads the trusted image catalog from `VMImageRoot()/catalog.json`, requires the trusted `qemu-img` helper, then connects to the canonical local `qemu:///system` control plane. Any missing prerequisite or authorization error fails closed; the CLI never retries the lab through Podman.

Normal VM command lines are passed as the argument to `/usr/bin/bash -lc` **inside the guest** through QEMU Guest Agent, while grading continues to use structured state probes. Raw serial streaming is exposed only through the explicit `:console` command, with a local escape and bounded cancellation behavior; it is not a generic host terminal fallback.
